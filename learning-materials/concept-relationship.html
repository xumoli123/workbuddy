一句话读懂三者关系

Agent 是"会干活的人"，上下文 是"他面前的桌面"，Skill 是"抽屉里的操作手册"。人围着桌面工作，手册按需从抽屉抽出来摊到桌面上——桌面放不下所有手册，也不需要一次全摊开。

上下文如何影响 Agent 的运行

Agent 每一轮"思考 → 行动 → 观察"循环，本质上都是把当前上下文交给大模型重新推理一次。因此上下文直接决定了 Agent 的三件事：

  • 能记住什么：上下文窗口有长度上限，放不下全部历史就要截断或压缩。被裁掉的内容 Agent 就"忘了"，所以长任务需要笔记、摘要等记忆管理手段。
  • 能看见什么：工具调用结果、用户偏好、当前任务说明，只有进入上下文模型才知道。上下文组织得越清晰，Agent 的决策质量越高——"桌面整洁，干活才快"。
  • 多花多少成本：上下文越长，每次推理的 Token 消耗和延迟越高。这也是 Skill 采用"渐进式披露"的原因：平时只在上下文里放一行"名称+描述"，匹配到任务才加载正文。

Skill 如何沉淀成可复用的任务知识

Skill 的价值在于把"一次会话里的经验"变成"下次直接能用的方法"，路径是：

  1. 经验文档化：把做好某类任务的步骤、注意事项、示例写成 SKILL.md（就像人把工作心得写成 SOP 手册）；
  2. 元数据索引：文件头部用 name + description 声明"这个技能是干什么的"，让 Agent 不用读全文就知道何时该用它；
  3. 按需加载：任务匹配时才把正文与配套脚本渐进式注入上下文，不占用日常空间；
  4. 跨会话复用：Skill 以文件形式存放在项目里（如 skills/ 目录），可以进 git 版本管理、团队共享、持续迭代——会话结束了，方法留下了。
一句话：上下文负责"这一次怎么干"，Skill 负责"这类活儿以后都怎么干"。
